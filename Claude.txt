> Explain the logic behind everything so I can understand it

● How Mango Grove works

  1. The core idea: UI = function of state

  React re-runs your component functions whenever state changes, and whatever
  they return is what's on screen. You never write "update the badge to 3". You
  change the cart state, and every component that reads it redraws itself.

  2. State lives in App.jsx

  App is the common parent of everything that needs shared data, so it owns the
  state:

  ┌─────────────────────────┬──────────────────────────────────────────┐
  │          State          │                 Used by                  │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ cart                    │ header badge, product cards, cart drawer │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ isCartOpen              │ drawer                                   │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ query, category, sortBy │ toolbar controls and product grid        │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ giftBox, promoCode      │ drawer and the totals                    │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ receipt                 │ order confirmation                       │
  └─────────────────────────┴──────────────────────────────────────────┘

  This is lifted state: if two components need the same data, it goes in their
  closest common parent. App passes values down as props and passes functions
  down so children can ask for changes. Data flows down, and events flow up
  through callbacks.

  The cart stores only { id, qty }. Names and prices are looked up from the
  catalog:

  const lines = cart.map((item) => ({ ...MANGOES.find(m => m.id === item.id),
  qty: item.qty }))

  Storing a copy of the price in the cart could let it drift out of sync.
  Keeping one source of truth avoids that.

  Derived values aren't state. visibleMangoes, lines, cartCount, quantities and
  totals are recomputed on every render from the real state. This is why the UI
  can't get out of sync: there's nothing extra to remember to update.

  3. Updating state without mutating

  React only re-renders when it gets a new value. arr.push() changes the old
  array, so React wouldn't notice. Every update builds a new array:

  setCart((current) => {
    const existing = current.find((item) => item.id === id)
    if (!existing) return [...current, { id, qty: 1 }]          // new array
  with one more item
    return current.map((item) =>                                 // new array,
  one item replaced
      item.id === id ? { ...item, qty: Math.min(item.qty + 1, MAX_PER_VARIETY) }
  : item)
  })

  Passing a function (current => ...) means "give me the latest state". That's
  safer than reading cart directly, which could be stale. Removing uses filter.
  Changing quantity uses map plus Math.min(Math.max(...)) to clamp between 1 and
  12.

  4. Search, filter, sort (utils/catalog.js)

  mangoes.filter(category matches).filter(name or origin contains
  query).sort(SORTERS[sortBy])

  - Each filter returns a new array, so .sort never reorders the original
    MANGOES.
  - SORTERS is a lookup object: the dropdown value picks a comparison function.
    "Featured" returns 0, which keeps the original order.
  - An empty search string matches everything, because "anything".includes("")
    is true.
  - ProductGrid renders an empty-state message with a "Clear filters" button
    when nothing matches. That is conditional rendering.

  5. Controlled inputs

  A controlled input's value comes from state, and typing calls a handler that
  updates that state:

  <input value={query} onChange={(e) => onQueryChange(e.target.value)} />

  React is the single source of truth for what the box shows. That's why "Clear
  filters" can empty the search box by setting query to ''. The sort <select>,
  the gift checkbox (checked={giftBox}) and the promo field work the same way.

  6. Lists and keys

  Every .map() gives each item a key that is a stable id: mango.id, line.id,
  category, perk.id, level. Keys let React match items between renders. If the
  list reorders (when you sort), React moves the existing cards instead of
  rebuilding them, and it doesn't mix up their state. An array index would break
  that. Perks does use position to print "01, 02…", but only for display, not
  as the key.

  7. Component by component

  - Header takes cartCount and onCartClick. It doesn't know what a cart is.
  - Hero takes featured (the first three mangoes) and maps them to MangoImages.
  - Toolbar composes SearchBar, CategoryTabs and the sort select. They're
    controlled by App's state.
  - ProductGrid decides empty state or results, then maps to ProductCards.
  - ProductCard computes what to show: "Sold out" if !inStock, "Box limit
    reached" if qtyInCart >= 12, otherwise "Add to box". The button is disabled
    in both unavailable cases. The "N in your box" badge appears only when
    qtyInCart > 0. It sets a CSS variable --tint from the mango's color, and the
    stylesheet tints the card background from it.
  - MangoImage is one SVG that takes colors as props, so one drawing becomes
    eight varieties. It uses useId() because SVG gradient ids must be unique on
    the page. With several mangoes visible, hard-coded ids would collide and the
    wrong gradient would show.
  - CartDrawer is always mounted. A CSS translateX slides it in and out, and the
    inert attribute keeps hidden buttons out of tab order. It shows one of
    three views: the receipt, the empty message, or the items. A useEffect adds
    an Escape-key listener while the drawer is open and removes it in the
    cleanup function, so listeners never pile up.
  - CartLine holds the −/+ stepper and Remove button. Minus is disabled at 1 and
    plus at 12.
  - PromoCode keeps its own local draft and error state, since nobody else needs
    to know a half-typed code. The applied code lives in App, because the
    totals depend on it. On submit it uppercases the input and checks code in
    PROMO_CODES. Typing again clears the error.
  - OrderConfirmation shows the receipt.

  8. Price math (utils/pricing.js)

  calculateTotals is a pure function: same inputs, same output, no state or side
  effects. That makes it easy to reason about and test.

  subtotal = Σ price × qty
  discount = subtotal × promo rate (0 if none)
  shipping = free if empty cart, or if (subtotal − discount) ≥ $40, else $6.95
  total    = subtotal − discount + giftFee + shipping

  Check against my test: 3 × 4.75 + 2.25 = 16.50, minus 10% = 14.85, plus 4.99
  gift, plus 6.95 shipping = 26.79. The free-shipping bar uses
  amountToFreeShipping from the same function.

  9. Checkout

  setReceipt({ number: ..., count: cartCount, total: totals.total })  //
  snapshot FIRST
  setCart([]); setPromoCode(null); setGiftBox(false)                  // then
  reset

  The receipt is copied before the cart is cleared, because the totals are
  derived from the cart. Math.random() for the order number lives in the click
  handler, not during rendering. Rendering should be predictable, and React's
  StrictMode runs it twice in development, which would give two different
  numbers. Closing the drawer sets receipt back to null.

  10. Styling and build

  - index.css defines design tokens (--mango, --leaf, etc.) on :root, so the
    theme is one place to change.
  - Each component imports its own .css file, and Vite bundles them all.
  - npm run build outputs static files to dist/. netlify.toml tells Netlify to
    run that command and serve that folder. There's no server, so the site is
    just files.

  5. Why PromoCode's draft is local but the applied code is in App.
